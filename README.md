# Website Technologies Scraper

A tool that identifies the technologies used to build a website, given a list of domains,
with proof attached to every detection. Built for the Veridion SW Engineer Intern challenge.

## How to run it

```
pip install -r requirements.txt
python3 main.py
```

That's it. `signatures.json` (the detection ruleset) and `domains.snappy.parquet` (the input
domain list) are both committed, so this runs out of the box. It fetches every domain in the
list, matches it against the signature database, and writes `results.json`.

`import_signatures.py` is a separate tool - it's what *generated* `signatures.json` from
[enthec/webappanalyzer](https://github.com/enthec/webappanalyzer), not something you need to
run to use the scraper. It isn't runnable as committed: it reads from a local clone of that
repository (`src/`), which is deliberately not included here, since its data is GPL-3.0
licensed (see Licensing below) and there's no reason to vendor a full third-party repository
into this one just to regenerate a file that's already committed.

## Architecture

```
fetch_modules/          one function per fetch concern: HTTP (headers, cookies, body),
                         DNS (Name Server, Mail eXchange, TXT, Canonical Name, Start of
                         Authority records)
        |
        v
detector.py              orchestrator - for each technology in signatures.json, checks
                         every one of its "sources" against the matching detector module,
                         collects whatever Evidence comes back
        |
        v
detector_modules/        one module per source type (html_body, headers, cookies, dns),
                         each a single generic match() function - no per-technology logic
                         anywhere, just source/field/match_type/pattern read from the
                         signature and applied uniformly
        |
        v
results.json             one record per domain: status, final URL, and every matched
                         technology with its category, the evidence that proved it, and a
                         confidence score
```

`signatures.json` is grouped one object per technology, each holding a `sources` list -
every signal that can identify it, from any of the four source types, with its own
`match_type` (`contains`, `regex`, `exists`, or `key_regex`) and confidence. A technology
matches if *any* of its sources fire; if several do, the reported confidence is the max
across them - corroborating evidence doesn't add extra weight, but it doesn't need to.

### Where the signatures come from

`signatures.json` is generated by `import_signatures.py` from webappanalyzer's technology
database, filtered by two things: the technology must carry a CPE identifier (a formal,
NIST-recognized "this is a real software product" marker - used as a quality bar, not an
arbitrary restriction), and it must have at least one signal in a source this project can
actually reach (`headers`, `cookies`, `meta`, `html`, `scriptSrc`/`scripts` - all reduce to
text already present in a plain HTTP fetch; `js`/`dom` fields are skipped entirely, since
they only exist after a real browser executes a page's JavaScript, which this project's
fetcher does not do).

Every regex pattern is tested against an adversarial string with a wall-clock timeout before
it's allowed into the file at all - a permanent guard against catastrophic backtracking
(see Main Issues, below), not something checked once and forgotten.

## Output

`results.json` - one entry per input domain:

```json
{
  "domain_name": "example.com",
  "status_code": 200,
  "status": "Success",
  "hasResponse": true,
  "final_url": "https://example.com/",
  "technologies": [
    {
      "technology": "WordPress",
      "category": "cms",
      "evidence": [
        {"source": "html_body", "contains": "<meta name=\"generator\" content=\"WordPress 6.4.3\" />", "confidence": 0.9}
      ],
      "final_confidence": 0.9
    }
  ]
}
```

`results_stats.txt` is a separate, plain-text technology-count summary - deliberately not
embedded inside `results.json` itself, since that file's entire value is being one uniform
array of per-domain records; mixing a differently-shaped summary object into it would break
that for anything that reads it expecting consistent records.

`signatures_no_cpe_experiment.json` and `results_no_cpe_experiment.json` are real, committed
evidence for the precision-vs-volume tradeoff discussed below - not narrated, inspectable.

## Debate topics

### What were the main issues with your current implementation, and how would you tackle them?

**Signature coverage is an open set for me, not a problem I expect to reach an end state on.**
No matter how much coverage I add, there will always be another domain with another pattern I
don't have yet - I've confirmed this is true of every general-purpose fingerprinting tool
(Wappalyzer, WhatWeb, BuiltWith included), not a flaw specific to my approach. The real,
structural constraint I'm working against is signature-database *breadth*: my database
currently holds 404 technologies, and I can't report more distinct technologies than I have
signatures for, no matter how precisely I match each one.

**I gave myself a CPE quality filter, and I measured its real cost before deciding to keep
it.** Dropping the CPE requirement grows my automated import from 404 to 5,787 technologies,
and my live detections on the 200-domain set from 39 to 236 (I kept both
`signatures_no_cpe_experiment.json` and `results_no_cpe_experiment.json` as evidence, not just
a described conclusion). That reads like a clear win until I checked what was actually behind
it: I spot-checked three of the less-recognizable names in that larger result and found one
confirmed false positive (`Trident AB`, which had matched literal browser-detection JavaScript
checking for Internet Explorer's rendering engine string, not any real use of a technology by
that name). A bigger database didn't just add correct detections for me, it also let a handful
of overly generic patterns through that my smaller, CPE-filtered set either excludes or never
happened to trigger. Given the challenge's own explicit requirement to "provide proof about how
you came to the conclusion," I kept the smaller, defensible number as my shipped default, and
kept the larger experiment as evidence for this tradeoff rather than adopting it outright
without a full precision audit.

**I found and permanently closed a catastrophic regex backtracking vulnerability.** While I was
running my no-CPE experiment, my detector hung for over ten minutes, unresponsive even to
repeated Ctrl+C (I confirmed the C-level regex engine doesn't yield back to Python's
interpreter mid-match, so SIGINT never gets a chance to run). I profiled every regex pattern
against one real page and found two patterns alone accounting for 45 of 48 total seconds across
2,201 patterns - both unanchored `.*X.*Y`-shaped patterns, a textbook case of catastrophic
backtracking. I fixed it by adding a permanent safety check to my import script: every regex
pattern is tested against an adversarial string with a 1-second timeout before I let it into
any output file, dropping and logging anything that fails. The same check caught a second,
already-shipped dangerous pattern that my earlier manual audit had missed, because that pattern
lived on a headers-sourced signature and my manual check had only covered `html_body`.

**My HTML matching is raw regex over response text, not a parsed DOM.** I made that tradeoff
for simplicity - real fingerprinting tools do the same for exactly this kind of check (only
DOM-dependent fields actually need a real browser), and every match I produce is still
confidence-scored, not treated as certain. It has a real failure mode I have to own: a pattern
can match text sitting inside an HTML comment or an unrelated script literal instead of live
markup. I found and fixed one concrete, related bug project-wide: a real page I inspected used
`<meta content="Microsoft Word 10" name="Generator">` (capital G) - HTML attribute names are
case-insensitive per spec, but my matching regex wasn't, so this and every other meta-tag-based
signature I had (roughly 100 of them) were silently blind to any page that capitalized its
attributes differently. I fixed it by scoping an inline case-insensitive flag to just my meta
co-occurrence patterns specifically, not my `scriptSrc`/`html` patterns, which check genuinely
case-sensitive file paths.

### How would you scale this solution for millions of domains crawled in a timely manner (1-2 months)?

I read "1-2 months" as engineering time, not execution time - the question I'm actually
answering is "if I had 1-2 months to build this properly instead of the week I gave myself,
and the target was millions of domains instead of 200, how would I change the project itself?"
I checked the other reading before dismissing it: my current, completely unchanged
single-machine setup processes 200 domains in about 80 seconds, which works out to roughly
216,000 domains a day run continuously - already well past the ~83,000/day a 5-million-domain,
60-day target would need. So if this were purely about execution-time budget, my honest answer
would be "no changes required," which can't be what's actually being asked - it would make the
question pointless. Here's what I'd actually build with real time:

**Fix the DNS bottleneck I already found, first.** Adding DNS as a fourth signal source showed
me that ~15% of real domains hit a multi-second timeout ceiling, and parallelizing my five
lookups per domain didn't fix it, because they all fail against the same unreachable nameserver
at once - parallelizing removes the *stacking* of that delay, not the delay itself. I traced the
actual cause: every DNS query on a Linux machine goes through one shared local resolver daemon
(`systemd-resolved`, listening on `127.0.0.53`) by default, regardless of how many threads or
processes are asking - it's a single, finite-capacity service shared by the whole machine, not
a per-request resource. I confirmed pushing concurrency past its real service rate doesn't
degrade gracefully - queries get dropped and retried instead of merely delayed, so my measured
latency actually got *worse* with more workers (`max_workers=200` was slower and less complete
than `max_workers=10`). The fix I'd apply, and it doesn't even need more machines: point my DNS
queries directly at a high-capacity public resolver (`8.8.8.8`, `1.1.1.1`) instead of my local
stub, bypassing the single-machine bottleneck entirely.

**Move from threads to processes to machines, in that order, for the right reason each time.**
My `ThreadPoolExecutor` already behaves like a self-balancing queue internally - each worker
pulls the next domain the moment it's free, which is why my current single-process
implementation doesn't suffer from static-split imbalance. But threads share one process and
one machine's resources; genuinely handling many domains at once at real scale needs multiple
processes (to get real multi-core parallelism for my CPU-bound regex-matching stage, which
Python's GIL prevents threads from ever achieving) and ultimately multiple machines (each with
its own network path and DNS resolution capacity, not a shared bottleneck). I'd avoid splitting
my domain list into static, pre-assigned shards, since that loses the same self-balancing
property `ThreadPoolExecutor` already gives me for free within one process - I've seen directly
that my domains aren't uniform in processing time, so I'd use a shared work queue across
processes/machines (a real queue system, or a "claim the next unprocessed row" table) instead
of a static split.

**Replace `results.json` with a real database before this stops being viable.** A single
multi-gigabyte JSON file isn't something I could load, grep, or recover from a mid-run crash.
I'd move to a real database (e.g. Postgres), which solves two of my problems at once: it
handles concurrent writes safely via transactions and row-level locking, something a flat file
structurally can't guarantee under multiple concurrent writers, and it gives me resumability
for free - a crashed worker just leaves its claimed rows unfinished, and a restart picks them
back up without me needing separate checkpoint logic.

### How would you discover new technologies in the future?

**I'd go automated first, since it's cheaper, and aggregate more sources than just
webappanalyzer.** I'd build a scheduled pipeline (e.g. a GitHub Action running on a timer) that
re-fetches multiple independent fingerprint sources, re-runs my import, and diffs the result
against what's committed - opening a PR or auto-committing when a source has genuinely updated.
I'd de-duplicate at the *signal* level, not the technology level, reusing the same merge logic
I already built for merging my DNS signatures into existing technologies: if a technology
already exists, extend its `sources` list; if a specific signal (source, field, and pattern) is
already present, skip it; otherwise add it. I want to be honest about a real, structural
limitation here: determining whether two *different* regex strings are semantically equivalent
isn't generally decidable by simple comparison, so my check can only ever catch exact-duplicate
patterns, never two sources expressing the same real-world signal in slightly different regex
syntax. Some redundant entries would always slip through for me - a small, accepted cost of
choosing automation over manually verifying every pattern by hand.

**I'd keep manual discovery as a second, deliberately separate layer.** It doesn't belong
inside my automated pipeline itself - a scheduled job can't have a human blocking it and stay a
pipeline. Instead, I'd use the pipeline's own `technologies: []` output as the target list for
a periodic, separate research pass of my own: systematically reviewing domains that still come
up empty after my automated sources have been checked - the same move that let me find a live,
uncaught `Microsoft Word` generator tag by hand during this project, just done deliberately and
off a queue instead of by accident.
